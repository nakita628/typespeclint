# API リントチェックリスト

[English](../en/api-lint-checklist.md)

typespeclint は、API リントチェックリストを TypeSpec 向けに自動化します。このページでは、チェックリストの各項目が何を確認するのか、どの typespeclint ルールが対応するのか、レビューに残るのは何かをまとめます。

## リントの位置づけ

API は実装の前に何度かレビューします。レビューごとに答える問いが違います。

| ステップ                            | 問い                                                     | 担当       |
| ----------------------------------- | -------------------------------------------------------- | ---------- |
| 1. ニーズを検証する                 | API は正しい解決策か。どのニーズに応えるのか。           | 人         |
| 2. 設計をリントする                 | インターフェイスコントラクトは設計ルールに従っているか。 | 主にツール |
| 3. プロバイダの視点でレビューする   | セキュアで、実装可能で、拡張可能か。                     | 人         |
| 4. コンシューマの視点でレビューする | 理解しやすく、使いやすいか。                             | 人         |
| 5. 実装を検証する                   | 実装は設計どおりのコントラクトを提供しているか。         | テスト     |

リントには 2 つの作業があります。設計上のバグ（プロパティの型の間違いなど）を見つけることと、設計がガイドラインに従い、既存の要素と一貫しているかを確認することです。セキュリティとドキュメントもリントの対象です。記述ファイルに書くものは、基本的にすべて対象になります。

リントが確認するのはコントラクトの形式で、内容ではありません。すべてのルールを通った設計でも、ニーズを取り違えていたり、使いにくかったりすることはあります。ステップ 2 を自動化する理由は 1 つです。ステップ 3 と 4 のレビュー担当者が、人にしか判断できないことに時間を使えるようになります。

## チェックリスト

表は区分ごとの項目です。最後の列は typespeclint がどこまで確認するかを示します。

- **自動**: ルールが判定します。
- **一部**: 機械的に決まる部分（説明があるかどうかなど）をルールが確認します。残り（説明が正確かどうかなど）はレビューで判断します。
- **レビュー**: ルールはありません。人が確認します。

区分の名前は `typespeclint.config.ts` の `categories` にそのまま使えます。

### 進化（`evolution`）

以下のすべての項目に当てはまります。

| チェック   | 確認すること                                                                     | typespeclint                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 破壊的変更 | コンシューマを壊す変更が本当に必要か。必要ならバージョニングポリシーを適用する。 | 一部: `breaking-change` が、記録しておいたベースラインと比較して、壊れる変更を報告します。変更が必要かどうかは人が判断します。 |

### API のセキュリティ定義（`security`）

| チェック     | 確認すること                                                                                            | typespeclint                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 使われている | すべてのセキュリティ定義が使われている。使われていない定義は、`@useAuth` の付け忘れか不要なコードです。 | 自動: `security-scheme-used`                                                                               |
| 有効である   | 種類に応じたマシンリーダブルな情報があり、ガイドラインに従っている。                                    | 自動: `security-scheme-valid`                                                                              |
| 説明が有効   | 各スコープに適切な説明がある。                                                                          | 一部: `security-scope-valid` がスコープ名を確認します。TypeSpec にはスコープの説明を書く構文がありません。 |

### API のゴールフロー（`flows`）

ゴールは、コンシューマが API で達成すること、つまり 1 つのオペレーションです。フローは、あるユースケースで呼び出すゴールの並びです。

| チェック   | 確認すること                                                       | typespeclint                                            |
| ---------- | ------------------------------------------------------------------ | ------------------------------------------------------- |
| 有効である | フローの振る舞いがガイドラインに従い、既存のフローと一貫している。 | レビュー                                                |
| 説明が有効 | ユースケースが API かゴールの説明に書かれている。                  | 一部: `operation-documented` が説明の有無を確認します。 |

### モデル（`models`）

| チェック         | 確認すること                                         | typespeclint                                                        |
| ---------------- | ---------------------------------------------------- | ------------------------------------------------------------------- |
| 使われている     | すべてのモデルがゴールから使われている。             | 自動: `model-used`                                                  |
| 名前が有効       | 名前がガイドラインに従い、既存の名前と一貫している。 | 自動: `model-naming`                                                |
| データ構造が有効 | 構成と深さがガイドラインに従っている。               | 一部: `model-structure` が深さとプロパティ数を制限します。          |
| 説明が有効       | ヒューマンリーダブルな説明があり、正確である。       | 一部: `model-documented` と `example-required` が有無を確認します。 |

### モデルのプロパティ（`properties`）

| チェック               | 確認すること                                                                                     | typespeclint                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 名前が有効             | 名前がガイドラインに従っている。`err_msg` ではなく `errorMessage`。                              | 自動: `property-naming`                                                     |
| 必須ステータスが有効   | オプションと必須が意図どおりである。すべてのプロパティがオプションのモデルは、おそらく誤りです。 | 一部: `property-required` が全プロパティオプションのモデルを見つけます。    |
| 型とフォーマットが有効 | 型とフォーマットが名前、値、説明に合っている。ISO 8601 の日付は文字列ではなく日付型にする。      | 一部: `property-type` と `standard-format` が名前に基づく規約を適用します。 |
| 説明が有効             | ヒューマンリーダブルな説明と、マシンリーダブルな制約（`minimum` など）が有効である。             | 一部: `property-documented` が有無を確認します。                            |

### ゴール（`operations`）

| チェック                   | 確認すること                                                                                                     | typespeclint                                                               |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 分類されている             | ゴールが分類されている。義務ではありませんが、API が読みやすくなります。                                         | 自動: `operation-tagged`                                                   |
| パスが有効                 | パスのフォーマットがガイドラインに従い、成功レスポンスの種類にも合っている。定義されたパスパラメータが存在する。 | 自動: `operation-path`。パスパラメータの宣言は TypeSpec 自体が確認します。 |
| HTTP メソッドが有効        | メソッドがガイドラインに従い、ゴールの内容にふさわしい。                                                         | 一部: `operation-method` がオペレーション名からメソッドを推定します。      |
| 成功とエラーに対処している | 成功と失敗に必要なすべてのレスポンスを返す。                                                                     | 一部: `operation-responses` がそれぞれ 1 つ以上あることを確認します。      |
| セキュア                   | セキュリティメカニズムがゴールをカバーしている。                                                                 | 自動: `operation-secured`                                                  |

### ゴールのパラメータ（`parameters`）

| チェック               | 確認すること                                                                                                                              | typespeclint                                                                          |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 名前が有効             | 名前が位置ごとのガイドラインに従っている。                                                                                                | 自動: `parameter-naming`                                                              |
| 必須ステータスが有効   | パスパラメータは必須である。作成や置換のボディで全プロパティがオプションなのは、おそらく誤りです。                                        | 自動: `parameter-required`                                                            |
| 型とフォーマットが有効 | 型とフォーマットが位置に対して有効である。クエリパラメータにオブジェクトを使わない。パスパラメータに URL で禁止されている文字を含めない。 | 一部: `parameter-type` と `standard-format`                                           |
| 説明が有効             | 説明と制約が有効である。                                                                                                                  | 一部: `parameter-documented` が有無を確認します。                                     |
| 位置が有効             | 位置が HTTP メソッドに合っている。削除リクエストにボディを付けない。センシティブな値を URL に含めない。                                   | 自動: `parameter-location`                                                            |
| 提供可能               | コンシューマが各パラメータを提供できる。値を知っているか、別のゴールから取得できる。                                                      | 一部: `parameter-providable` が、各識別子を返すオペレーションがあることを確認します。 |

### ゴールのレスポンス（`responses`）

| チェック              | 確認すること                                                                           | typespeclint                                                                                                       |
| --------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| HTTP ステータスが有効 | ステータスがガイドラインに従い、レスポンスの種類に合っている。                         | 自動: `response-status-code`                                                                                       |
| ボディが有効          | ボディの型とフォーマットがステータスに合っている。エラーは標準のエラーモデルを使う。   | 自動: `response-error-body`、`response-problem-details`（オプトイン、RFC 9457）                                    |
| ヘッダーが有効        | ヘッダーの名前、型、フォーマットがガイドラインに従っている。                           | 一部: `response-header-naming` が名前を確認します。                                                                |
| 使われている          | レスポンスで返すデータが実際に使われている。                                           | レビュー                                                                                                           |
| 成功の説明が有効      | 成功レスポンスの説明とモデルが有効で正確である。                                       | 一部: `response-documented` が説明の有無を確認します。                                                             |
| エラーの説明が有効    | エラーが役に立つ詳細を、ヒューマンリーダブルに、可能ならマシンリーダブルにも提供する。 | 一部: `response-documented` が説明の有無を、`response-error-body` と `response-problem-details` が形を確認します。 |

## `recommended` で対応できる範囲

上のリントチェックリストには 31 の項目があります。`typespeclint/recommended` を有効にしただけの状態（追加の設定なし）では、次のようになります。

| 対応                         | 項目数 | 内容                                                             |
| ---------------------------- | ------ | ---------------------------------------------------------------- |
| `recommended` のルールが動く | 29     | 上の表で「自動」または「一部」とした項目すべて。                 |
| ルールを作れない             | 2      | ゴールフロー「有効である」。ゴールのレスポンス「使われている」。 |

対応できない 2 項目は、TypeSpec の記述に含まれない情報を必要とします。フローがどう振る舞うか、コンシューマが受け取ったデータを使っているか、です。レビューで確認します。

ルールが動くことは、保証されることと同じではありません。29 項目は、検査の深さが違います。

| 深さ           | ルールが判断すること                                                                   | 項目                                                                                                                                             |
| -------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 形式           | 宣言を完全に判定します。                                                               | 命名、パスのフォーマット、ステータスコード、使われていないモデルとセキュリティ定義、セキュリティのカバー範囲、パラメータの位置、必須ステータス。 |
| 有無           | 書かれているかどうか。正確かどうかはレビューで判断します。                             | 「説明が有効」の項目すべて。モデル、プロパティ、パラメータ、オペレーション、レスポンス。                                                         |
| 名前からの推定 | 名前から期待される内容を確認します。命名の流儀が違うと、見逃しや誤検知が起こりえます。 | HTTP メソッド（オペレーション名から）、型とフォーマット（プロパティ名から）、パラメータの提供可能性（`*Id` から）。                              |
| 項目の一部     | TypeSpec から読み取れる範囲だけ。                                                      | スコープ（名前のみ。説明を書く構文がありません）、ヘッダー（名前のみ）、破壊的変更（オペレーションの入出力のみ。振る舞いは対象外）。             |

次の 3 つのルールは、チェックリストの範囲を超えるので `recommended` に入っていません。`example-required`、`standard-format`、`response-problem-details` です。使う場合は `typespeclint.config.ts` で有効にします。

既存の API に `recommended` を導入するときは、次の 2 点に注意してください。

- 「説明が有効」のルールは、説明のないプロパティ、パラメータ、レスポンスをすべて報告します。これらのルールなしで書かれた API では指摘が多く出ますが、どれも正しい指摘です。
- `breaking-change` は、ベースラインを記録するまで「ベースラインがない」と報告します。`TYPESPECLINT_UPDATE_BASELINE=1 tsp compile . --no-emit` で記録します。

## 注意が必要な 3 種類のチェック

ほとんどのチェックは単純で、結果は合否のどちらかです。次の 3 種類はそうではありません。

**ドキュメント。** コントラクトが包括的に文書化されていると、プロバイダとコンシューマの視点でのレビューがずっと楽になります。ツールは説明があることを要求できます。説明が正しいかどうかは人が判断します。

**フロー。** コンシューマがユースケースを実際にたどれるかの確認は単純ですが、API が動くことを示すうえで欠かせません。パラメータを提供できないコンシューマは、そのゴールを使えません。

**既存の要素との一貫性。** 最も難しく、最も重要なチェックです。名前、データモデル、振る舞いを、その API の他の部分、組織の他の API、標準規格とそろえます。これを怠ると、同じものが 3 通りに表現されることになります。組織の API 全体を 1 人で把握することはできないので、API のドキュメントを使い、検索できるようにしておきます。フォーマットを自作する前に、既存の規格を探してください。日付は ISO 8601、通貨は ISO 4217、電話番号は E.164 です。規格が見つかったらガイドラインに追加します。API に必要な規格の目録はすぐにできあがります。既存の API を進化させるときは、破壊的変更にならないかも確認します。typespeclint では、`typespeclint.config.ts` の `conventions` か `custom` に追加します。

## ニーズの検証

URL や HTTP メソッドを考える前に、できるだけ早い段階で行います。最初に想像したニーズと本当のニーズは、しばしば違います。たとえば、あるチームが「任意のアドレスに任意の内容のメールを送る API」を設計します。なぜ必要なのかを尋ねると、本当のニーズは「プロファイルが変更されたことを顧客に知らせる」ことだと分かります。安全な解決策は REST API ではなく、通知システムが購読するイベントでした。

唯一の正しい方法はありません。次の質問が出発点になります。

| 観点                       | 質問                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ニーズ                     | 何をしたいのか。コンテキストは何か。解決策はどう使われるのか。ターゲットのコンシューマとエンドユーザーは誰か。答えに対して「なぜ」を 5 回ほど繰り返し、根本のニーズを特定する。本当のニーズがだいたい分かったら、API のゴールキャンバスを埋める。                                                                                                                              |
| コンシューマのコンテキスト | コンシューマとエンドユーザーは誰か（業界規格、国際化、セキュリティの方向性が決まる）。コンシューマに制約はあるか（XML しか使えない、PATCH を使えないなど）。コンシューマがすでに使っている業界規格はあるか。あれば新しいフォーマットより優先する。ネットワーク環境はどうか。エクスペリエンス API や BFF が必要になることがある。                                               |
| プロバイダのコンテキスト   | 既存のシステム、API、チーム、パートナーのうち何が必要か。依存関係は早めに特定する。技術的な制限はあるか（24 時間動かない、非同期のみ、応答が遅い、スケールしない）。機能的な制限はあるか（既存システムのビジネスルールがニーズに合わないなど）。処理に人が関与するか。どんな種類のコミュニケーションと API が必要か。そもそも API は解決策なのか、解決策の一部にすぎないのか。 |
| セキュリティ               | API はセンシティブなデータやアクションを扱うか。答えによって設計と実装が変わる。                                                                                                                                                                                                                                                                                               |

この作業は反復的で、ニーズを定義する人、実装する人、セキュリティを担当する人が参加します。既存の API に新しいゴールを足す場合も、新しい API を作る場合も、API ではないものを作る場合も同じです。

## プロバイダの視点でのレビュー

リントを通った設計が、プロバイダから見て問題ないとは限りません。ニーズを満たし、セキュアで、実装でき、進化できることをチーム全体で確認します。どの区分でも、同じいくつかの基準を繰り返し確認します。

| 基準                 | 対象                                                                                                                                             | 確認すること                                                                                                                                                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ニーズと一致している | フローとゴール（目的）、モデル（データ構造）、プロパティとパラメータ（必須ステータス、型とフォーマット、値）、レスポンス（成功とエラーのデータ） | 期待される概念を表していて、余計なものがない。成功レスポンスがそろっている。エラーレスポンスが、入力のチェック、機能的なエラー、セキュリティエラー、技術的なエラーを網羅している。                                                    |
| セキュア             | セキュリティ定義（スコープ）、プロパティ（値）、ゴール（パス、カバー範囲）、パラメータ（データ、位置）、レスポンス（成功とエラーのデータ）       | スコープがセキュリティ分割に合っている。センシティブなデータを不当に公開も要求もしていない。必要な場合は安全な表現と安全な位置で扱う。センシティブなデータを URL に含めない。ゴールが想定したスコープとメカニズムでカバーされている。 |
| 存在している         | プロパティの値、成功とエラーのデータ                                                                                                             | 実装が、直接または依存関係を通じて、そのデータを実際に提供できる。パラメータとして使うデータはリクエストできる。                                                                                                                      |
| 実装可能             | ゴール                                                                                                                                           | 直接または依存関係を通じて実装できる。                                                                                                                                                                                                |
| パフォーマンス       | フロー（累積）、ゴール                                                                                                                           | パフォーマンスの推定値がニーズに合っている。                                                                                                                                                                                          |
| 拡張可能             | すべての区分                                                                                                                                     | 将来の進化を合理的に考慮している。                                                                                                                                                                                                    |

typespeclint が確認するのは機械的な部分だけです。カバー範囲は `operation-secured`、URL のセンシティブな値は `parameter-location`、成功とエラーのレスポンスの有無は `operation-responses` が確認します。

## コンシューマの視点でのレビュー

API のことを何も知らないコンシューマになりきります。ゴール、パラメータ、レスポンス（特にエラー）がそのコンシューマにとって意味を持ち、プロバイダの内部を不当にさらしていないことを確認します。

| 区分               | 確認すること                                                                                                                                                                                                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| セキュリティ定義   | スコープがコンシューマにとって意味がある。                                                                                                                                                                                                                                                                               |
| ゴールフロー       | ゴールがエラーを防ぐ（振替の前に有効な受取口座を一覧するゴールなど）。ステップの数ができるだけ少ない。パフォーマンスの推定値がコンシューマに合っている。各ステップに意味がある。                                                                                                                                         |
| モデル             | 構造、深さ、詳細さが理解しやすく使いやすい。パラメータのモデルは最小限のプロパティにする。名前が簡単に理解できる。`aDTO` ではなく `Account`。                                                                                                                                                                            |
| モデルのプロパティ | 本当に必要なものだけが必須である。名前が明確である。`ts` ではなく `source`。型とフォーマットが理解しやすく使いやすい。Unix タイムスタンプではなく ISO 8601 の日付、`"2"` ではなく `"CHECKING"`。値がすぐに使える。誕生日に年齢を添える、コードにローカライズされたラベルを添える、テクニカル ID ではなく口座番号を使う。 |
| ゴール             | パスとそのパラメータの構造と名前が簡単に理解できる。ゴールがコンシューマにとって意味がある。パフォーマンスの推定値がコンシューマに合っている。                                                                                                                                                                           |
| ゴールのパラメータ | プロパティと同じです。最小限で、名前が明確で、型とフォーマットが分かりやすく、値が使いやすい。コンシューマが各パラメータを提供できる。                                                                                                                                                                                   |
| ゴールのレスポンス | 成功時に、必要なデータがすべて、情報価値のあるデータ（何が行われたか、次に何をすべきか）とともに返る。エラー時に、問題の解決を実際に助ける、包括的で情報価値のあるフィードバックが返る。                                                                                                                                 |

パフォーマンスは、基本的なユースケースと複雑なユースケースの両方で確認します。チームの外の人、できれば将来のコンシューマに設計を見てもらうことをためらわないでください。

typespeclint が助けになるのは、上の名前と型の例（`model-naming`、`property-naming`、`property-type`）です。残りは人が判断します。

## 実装の検証

すべてのレビューが終わると、API を実装できます。設計者は、実装が設計どおりのコントラクトを提供しているかの確認に協力することがあります。実装のテスト方法はここでは扱いません。注意点をいくつか挙げます。

- **セキュリティテストを省かない。** アクセス制御には 2 つのレベルがあります。登録済みのコンシューマだけが、許可されたスコープの中でだけ API を呼べること。そして、エンドユーザーの代理で動くコンシューマが、そのエンドユーザーに許されたものにだけ届くこと。センシティブなデータは不当に返さず、必要な場合は保護します。
- **生成されたドキュメントとの比較は慎重に。** コードから生成した記述ファイルで検証できるのは、生成のために足したアノテーションに依存しない要素だけです。「このプロパティの値は 2 種類」というアノテーションは、コードがその 2 つだけを返す保証になりません。
- **コントラクトを実行時に確認する。** 「必須プロパティがなければ 400 を返す」とコントラクトに書いてあっても、テストで確かめるまでは宣言にすぎません。
- **レスポンスのプロパティの仕様を確認する。** 必須と宣言したプロパティは、常に返さなければなりません。最小値、最大値、配列の要素数も同じです。
- **ネットワークチェーン全体をテストする。** ファイアウォール、プロキシ、API ゲートウェイが、メソッドをブロックしたり、ステータスを置き換えたり、別のフォーマットでエラーを返したりすることがあります。

typespeclint は実装をテストしません。

## 情報提供と共有

API の設計者は 1 人で作業するわけではありません。設計は共有できなければなりません。

- 標準の API 記述フォーマットを使い、ファイルをソース管理システムに置く。
- ガイドラインを理解しやすくし、すべての設計者にその存在を知らせる。
- 既存の API とデータモデルを簡単に見つけられるようにする。できれば検索可能にする（ソース管理システム、wiki、API カタログ、開発者ポータル）。一貫性のチェックはこれに頼ります。
- 自分の設計を同僚にレビューしてもらい、他の人のレビューにも参加する。API 設計者のコミュニティに参加するか、立ち上げる。何より、実際のコンシューマに設計をレビューしてもらう。

レビューでは、設計者は自分の設計をあらゆる面から疑い、正当性を説明します。目的は API をよりよく成長させることで、専門家の意見を全員に押し付けることではありません。

## typespeclint でチェックリストを使う

```ts
import { defineConfig } from 'typespeclint'

export default defineConfig({
  // お勧めのルールを warning で有効にする
  extends: ['recommended'],

  // チェックリストの区分をまとめて設定する
  categories: {
    security: 'error',
  },

  // ルールごとに重大度とオプションを設定する
  rules: {
    'response-problem-details': 'error',
    'property-naming': ['warn', { case: 'snake_case' }],
  },
})
```

すべてのルールの目的と NG / OK 例は [typespeclint の README](../../packages/typespeclint/README.md) にあります。この形で設定したプロジェクトの例は [`examples/config`](../../examples/config) にあります。

## カスタムルールの作り方

チェックリストには「ガイドラインに従っている」という項目が繰り返し出てきます。組織のガイドラインには、組み込みルールでは確認できないものもあります。そうした規則は、`typespeclint.config.ts` にカスタムルールとして書きます。

### 1. ルールを宣言する

ルールは、名前、説明、オプションの既定値、そして API を見て指摘を報告する `run` 関数でできています。

```ts
import { defineRule } from 'typespeclint'

// ガイドライン: 金額に浮動小数点数を使わない
const noFloatAmount = defineRule<{ names: string[] }>()({
  name: 'no-float-amount',
  description: 'Amounts must not be floating-point numbers.',
  category: 'properties',
  defaults: { names: ['amount', 'price', 'total'] },
  run({ analysis, options, report }) {
    for (const model of analysis.models) {
      for (const property of model.properties.values()) {
        const type = property.type
        if (
          options.names.includes(property.name) &&
          type.kind === 'Scalar' &&
          type.name.startsWith('float')
        ) {
          report(property, `'${property.name}' is an amount: use decimal, not ${type.name}.`)
        }
      }
    }
  },
})
```

| フィールド    | 意味                                                                                                                                                                                                  |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`        | ルールの名前。kebab-case で書きます。指摘は `typespeclint/<name>` として報告されます。組み込みルールと同じ名前は使えません。                                                                          |
| `description` | ルールが何を要求するかを 1 行で書きます。                                                                                                                                                             |
| `category`    | 省略できます。ルールが属するチェックリストの区分（`evolution`、`security`、`flows`、`models`、`properties`、`operations`、`parameters`、`responses`）です。指定すると `categories` の設定が効きます。 |
| `defaults`    | オプションの既定値。オプションのないルールは `{}` にして、`defineRule()` で宣言します。                                                                                                               |
| `run`         | コンパイルごとに 1 回呼ばれます。指摘は `report(target, message)` で報告します。                                                                                                                      |

`defineRule<...>()` に渡す型がオプションの型です。これにより、`rules` に書くオプションが型チェックされます。

### 2. API を調べる

`run` には、集め終わった API が渡されます。ルールが自分でプログラムをたどる必要はほとんどありません。

| プロパティ                | 内容                                                                                                           |
| ------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `analysis.models`         | プロジェクトで宣言した名前付きのモデル。                                                                       |
| `analysis.operations`     | プロジェクトで宣言したオペレーション。                                                                         |
| `analysis.httpOperations` | 同じオペレーションを HTTP オペレーションとして見たもの。`verb`、`path`、`parameters`、`responses` を持ちます。 |
| `analysis.services`       | HTTP サービスと、その認証。                                                                                    |
| `options`                 | `defaults` に設定ファイルの値をマージしたもの。                                                                |
| `program`                 | TypeSpec のプログラム。`getDoc(program, type)` など、コンパイラの API で調べるときに使います。                 |

typespeclint は、組み込みルールが使っている関数も公開しています。名前には `matchesCase` と `splitWords`、HTTP オペレーションには `describeOperation`、`statusClass`、`formatStatus`、型には `isUserType` と `ownDataProperties` が使えます。

オペレーションのルールも同じ形です。

```ts
import { defineRule, describeOperation } from 'typespeclint'

const noRpcPath = defineRule()({
  name: 'no-rpc-path',
  description: 'Paths name resources, not actions.',
  category: 'operations',
  defaults: {},
  run({ analysis, report }) {
    for (const operation of analysis.httpOperations) {
      if (/\/(send|create|update|delete|get)[-_/]/.test(`${operation.path}/`)) {
        report(operation.operation, `${describeOperation(operation)}: the path names an action.`)
      }
    }
  },
})
```

### 3. 指摘を報告する

`report(target, message)` には、指摘の対象になる型とメッセージを渡します。

- できるだけ細かい対象に報告します。モデルではなくプロパティ、インターフェイスではなくオペレーションです。指摘はその宣言の位置に表示されます。
- メッセージには、何が問題で、どう直せばよいかを、対象の名前と一緒に書きます。
- プロジェクトの外（ライブラリ）で宣言された型への指摘は捨てられます。API の作者が変更できるものに報告してください。

### 4. 登録して設定する

```ts
import { defineConfig } from 'typespeclint'

export default defineConfig({
  extends: ['recommended'],
  customRules: [noFloatAmount, noRpcPath],
  rules: {
    'no-float-amount': ['error', { names: ['amount', 'balance'] }],
  },
})
```

`customRules` に入れたルールは warning で動きます。`rules` では、組み込みルールと同じ設定が使えます。`'off'`、`'warn'`、`'error'`、またはオプション付きの `['error', { ... }]` です。意図した違反は、宣言の位置で抑制します。

```tsp
#suppress "typespeclint/no-float-amount" "exchange rate, not an amount"
model Rate { amount: float64; }
```

### 5. ルールを保守する

ルールはガイドラインの一部です。組み込みルールと同じ形で、目的、違反する例、通る例を書いておきます。そのうえで、2 つの例を TypeSpec としてリポジトリに置き、lint にかけます。どの例でも発火しないルールは、気づかないうちに動かなくなりがちです。

上の 2 つのルールは [`examples/banking/typespeclint.config.ts`](../../examples/banking/typespeclint.config.ts) にあります。
